## 3. A collision Python accepted and TypeScript caught

The field was called `coverage`. `SuccessionCoverageResponse` already has a field of that name — its own list of critical roles and successor counts.

**Python took the later definition and silently replaced the succession list. The entire suite still passed: 167 tests, green.** Nothing in Pydantic warns on a duplicate field name; the model simply resolves in favour of the last one. It surfaced only because the TypeScript compiler refused the same duplicate in `types.ts`.

Renamed to **`coverage_notes`**, which is clearer next to succession coverage anyway. Two tests now guard it:

- one pins that `SuccessionCoverageResponse.coverage` still holds `SuccessionCoverageItem`;
- one is general — it reads every schema source and fails on **any** field name defined twice in a class, because a shadowed field cannot be found by inspecting `model_fields` after the fact.

Worth stating plainly: had the new field been named `notes`, or had the frontend types not been generated by hand, this would have shipped. It is the second time this month a guardrail from one layer has caught a defect in another.

## 4. Two gaps the end-to-end proof exposed

The unit tests passed before either was found. Both came out of walking the real API.

**(a) The most-read surface had no note.** `@suppressible` calls `note_coverage` for the 56 decorated routes, but the 10 hand-wired column-mode endpoints — every KPI summary, the command-centre overview, the executive summary — bypass the decorator. They carried no coverage note at all, which is precisely backwards: the KPI strip is the surface with the em dash and the one a client reads first. Fixed with an explicit `prov.note_coverage(mart)` in each. **9 → 13 endpoints.**

**(b) The blocks were dicts assigned to typed fields.** `List[SuppressionItem]` receiving `dict` — Pydantic serialises it and emits `UserWarning: Expected CoverageItem but got dict`. It worked, so it had gone unnoticed **since step 2b**. `block()` and `coverage_block()` now build the models. A warning nobody reads is how the next shape mismatch gets through.

## 5. `covered_days` — the definition, pinned with its reasoning

Ruling 2 asked for this specifically, as the definition most likely to be "corrected" by a future reader. The test asserts against the shipped SQL and carries the argument in the assertion message:

```python
assert "coverage_status = 'covered'" in sql, (
    "covered_days must be counted from coverage_status, which is the "
    "DECLARED window - not from attendance_date, which is rows")
assert "attendance_date" not in sql, (
    "counting rows would double-count what Category F separated: a day "
    "inside the window with no row is an absence, not missing coverage")
```

A day inside the declared window with no attendance row is a **real absence** — Category F's central inversion. Counting rows here would recast it as missing coverage, and would quietly shrink the window back to whatever happened to arrive, which is the inference ruling 3 of Category F exists to forbid.

## 6. Not a suppression — enforced, not just documented

`coverage_notes` is a sibling block with its own type, its own component and its own visual weight. Four tests hold the line:

| Test | Holds |
|---|---|
| a partially-covered payload is still **served** | `payload()` returns True, `suppressed` stays empty, the note is present |
| an absent domain gets **one** explanation | `suppressed` fires, `coverage_notes` stays empty |
| the two blocks are separate keys with different types | they cannot be merged by accident |
| full coverage emits nothing | the noise rule |

On the frontend, `NotProvided` **replaces** content ("nothing is here yet") and `CoverageNote` **sits beside** it ("this is real, over less than you assume"). Conflating them visually would undo the distinction at the last step.

## 7. The em dash has its reason

Category F introduced a KPI card showing `—` when a metric is unmeasurable, with nothing explaining it. `KpiCard` now takes an `unmeasurableReason` and renders it under the dash; the Attendance page passes the coverage message. An em dash without a reason is indistinguishable from a bug — and a client who thinks a number is broken asks for it to be "fixed", which is how a fabricated number gets restored.

## 8. The meta-envelope decision — recorded, not built

Per ruling 5, recorded **in the plan doc** (§8), not in a commit message, because a commit message is not where a future contributor looks before adding a field:

> **Named trigger: the THIRD cross-cutting response field adopts a shared `meta` envelope.** `suppressed` and `coverage_notes` are the first two. A third must not be added as a third parallel list by default; reaching for one is the signal that the envelope is owed, and the work is to introduce `meta` and migrate all three together.

§3 of this report is evidence for the trigger rather than against it: two parallel lists are already enough to produce a silent name collision.

**Also settled at execution:** Western digits inside Arabic text, everywhere, matching every bilingual message 2b and Category F already ship. A test asserts no Arabic-Indic digit appears in a coverage message.
